# RTX 3090 Runbook

The RTX 3090 is the primary development target for the next experiments. Its
24 GB of VRAM is enough for the included presets, long toy lifetimes, and later
small text-encoder experiments.

## Environment Check

Install a recent NVIDIA driver, `uv`, and a CUDA-enabled PyTorch build. Confirm
that PyTorch sees the GPU:

```bash
nvidia-smi
UV_CACHE_DIR=.uv-cache uv run --with torch python - <<'PY'
import torch
print("torch:", torch.__version__)
print("cuda available:", torch.cuda.is_available())
print("gpu:", torch.cuda.get_device_name(0) if torch.cuda.is_available() else "missing")
PY
```

Run the tests and benchmark:

```bash
UV_CACHE_DIR=.uv-cache uv run --with torch --with pytest python -m pytest -q
UV_CACHE_DIR=.uv-cache uv run --with torch python -m rmc.probe --device cuda
bash scripts/benchmark_3090.sh
bash scripts/benchmark_3090.sh --preset 3090 --steps 10 --warmup 3
```

The probe is a small acceptance test for the model idea. It trains a fresh
four-action mapping task and compares normal retrieval against the same trained
core with external memory disabled. On the development M5 CPU, the addressed
memory implementation reached `1.000` query accuracy by step `700`; the
core-only ablation remained near `0.36`.

The first compiled call is intentionally slower because `torch.compile` traces
and builds optimized kernels. The training curriculum has three fixed lifetime
shapes, so the first update after each stage transition can compile another
graph. Judge steady-state throughput after warmup.

The benchmark prints a CUDA preflight snapshot. If background utilization is
already above `10%`, treat its throughput as a shared-card coexistence result.
Peak RMC memory allocation remains useful, but compare accelerator speed only
during a quiet window.

## Experiment Ladder

Begin with the debug preset:

```bash
bash scripts/train_3090.sh \
  --preset 3090-debug \
  --steps 6000 \
  --stage-steps 2000 \
  --evaluate-every 100 \
  --output-dir runs/3090-debug
```

`--steps` controls the total run length. `--stage-steps` controls how long each
curriculum stage remains active before progressing. Keep these separate during
short debugging runs so the model has time to master single-channel storage
before A -> B -> A retention begins.

Only move to the larger run after evaluation accuracy rises materially above
the random `0.125` baseline:

```bash
bash scripts/train_3090.sh
```

Resume an interrupted run:

```bash
bash scripts/train_3090.sh \
  --resume runs/3090/latest.pt \
  --output-dir runs/3090
```

Train a recurrence-only ablation:

```bash
bash scripts/train_3090.sh \
  --preset 3090-debug \
  --no-memory \
  --output-dir runs/3090-debug-core-only
```

Evaluation uses the current curriculum stage and reports
`core_only_revisit_acc` with external memory disabled. External memory earns its
complexity only when it beats that ablation. Earlier versions always evaluated
the hardest final stage, which made stage-one progress harder to inspect.

## Shared GPU

When other compute jobs already occupy the card, use the gentler launch:

```bash
bash scripts/train_3090_shared.sh \
  --steps 6000 \
  --stage-steps 2000
```

This uses batch size `128` and sleeps `25 ms` after each update. Override either
setting when appropriate:

```bash
bash scripts/train_3090_shared.sh --batch-size 64 --sleep-ms 100
```

GPU contention makes wall-clock benchmarks noisy but does not invalidate the
learning experiment. Check `nvidia-smi`: if total VRAM approaches the card
limit, reduce batch size. If another job is latency-sensitive or the card stays
near its thermal limit, increase `--sleep-ms` or coordinate a quieter window.

A benchmark collected while another process already holds the GPU at `100%`
utilization is not a standalone RTX 3090 benchmark. Treat it as a measurement
of the compute share available at that moment. Peak VRAM remains useful.

## Memory Pressure

If the larger preset exhausts VRAM, lower batch size first:

```bash
bash scripts/train_3090.sh --batch-size 64
```

Then reduce `--memory-slots`, `--memory-size`, or `--reasoning-ticks`.
The launch scripts set `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` to
reduce fragmentation in changing workloads.

## Why These CUDA Options

The runner enables AMP with gradient scaling, TF32 matrix multiplication, and
fused AdamW on CUDA. It compiles the complete fixed-shape lifetime rollout
rather than compiling one tiny event at a time. The `3090` preset uses
`max-autotune-no-cudagraphs`: autotuning is useful for an overnight run, while
avoiding CUDA Graph capture keeps the stateful recurrent experiment easier to
debug.
